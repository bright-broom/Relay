# Relay デザインガイド

Version 0.3 / 2026-09-11 / 本番UI実装の基準

## 1. 目的と参照資料

**必要な情報を静かに整理し、少ない入力で次の仕事へ進める。**

営業だけでなく、事務・運用・顧客サポートの担当者にも分かる画面をつくる。視覚的な質と日々の操作速度を両立し、AIの提案や情報不足を正確に表す。

参考はユーザー提供の「NOT A HOTEL から学ぶアプリのデザインガイドライン」Version 2.0（日本語版、2026-09-07）。同資料は公開画面を基にした独立した分析であり、公式ブランド規定ではない。本書はその原則をRelayへ再構成したもの。元サイトの全画面・挙動・計測結果を独自に検証したとは扱わない。

参照文書で案内されているトークンJSON、native-kit、生成器、書体ファイル等は今回の添付には含まれていない。本書の値と部品はRelay用の仕様であり、元キットの57トークンを完全移植したものではない。原本・写真・映像・ロゴ・商用書体は公開リポジトリに含めない。

### 採用するもの・Relayで調整するもの

| 参照資料の考え方 | Relayへの適用 |
|---|---|
| 白・黒・薄いグレー、余白、控えめな線 | 全画面の土台 |
| 大きい対象面と静かな説明面 | 案件・元資料・抽出結果・根拠を役割別に配置 |
| 青または緑の主要操作 | 青を採用。最新のユーザー指定を優先し、独立した状態色は設けない |
| ピル型の操作、役割別の角丸 | 主操作・絞込・パネルで一貫したvariantを使う |
| 大きな写真・欧文ディスプレイ・暗い章 | 紹介ページで必要な場合のみ。業務画面に一律適用しない |
| 小さいJavaScript・外部パッケージなしの参照キット | RelayはTypeScriptとモダンなUIライブラリを使う |
| 一度だけ使う値や表示文言はページ側に置く | ユーザー要件を優先し、スタイル値と表示文言は中央管理する |

## 2. 情報設計

### 一つの領域に一つの主役

一覧では「見分ける」、詳細では「理解して判断する」、フォームでは「入力して進む」を主役にする。見出し、数値、バッジ、ボタンのすべてを強調しない。

主要操作は判断領域につき原則一つ。例えば更新案の確認では「反映する」が主要操作、「修正する」「却下」は副操作。画面全体で一つに制限する意味ではなく、独立した判断領域はそれぞれの操作を持てる。

### 関係の近い情報を近づける

ラベルと値、状態と理由、エラーと修正方法を離さない。余白の大きさは情報の関係を表す。広い余白を全項目へ一律適用せず、業務画面は操作の近さを保つ。

### 根拠を見られる状態にする

案件名と状態 → 要約と次の対応 → 根拠 → 不足事項 → 操作の順を基本とする。重要な矛盾・未確認事項を閉じた補足へ隠さない。資料がない場合は整ったデータ面と時系列を使い、装飾画像で埋めない。

### 入力負荷を減らす

- 通常の記録は「連絡方法」「結果」「保存方法」を選択する。補足は任意。「その他」の場合だけ具体的な内容を求める。選択内容から記録文を生成し、AIが確認した事実とは扱わない。
- 結果の「相手が了承」「応答なし」「確認・返答待ち」はタスクを完了にしない。「この対応を完了」と保存方法の「記録して完了」の明示的な選択が揃った場合のみ完了にする。
- 一覧の担当・表示条件・状態はプルダウンにまとめる。検索以外の定型条件を自由入力にしない。
- 戻る、詳細への移動、コピー、メニュー、検索など普遍的な操作はアイコン化し、操作名をホバー・フォーカス時に表示する。読み上げ名は翻訳リソースで管理する。業務固有の判断や完了操作は短い文言を残す。
- 画面のキャッチコピー・重複する説明・補助的なプロモーション面は除く。履歴・根拠・背景・任意メモを折りたたみ、デザイン仕様は項目選択後に表示する。文字サイズを下げて情報量を減らしたように見せない。
- 会話・活動から得た情報を事前入力し、出典と未確認箇所を見せる。
- 同じ顧客名・日付・担当を何度も入力させない。承認済み情報を再利用する。
- 不足項目だけを聞く。高度な設定は必要になったときに開ける。
- 検索条件・編集中の内容を保持し、画面遷移や失敗でやり直しを増やさない。
- 一括操作は変更対象と差分が分かる形で提供する。
- AIの提案を入力済みの確定情報に見せない。未知は「未設定」「確認が必要」と表す。

## 3. 色とテーマ

**メイン＝墨黒、サブ＝白、アクセント＝青の3色に限定する。** これはユーザーの最新指定に基づくRelayの配色。参照資料の補助色をそのまま増やさない。「メイン」は画面を黒く塗る比率ではなく、文字・構造を支える役割を意味する。読む面は白を主体とする。

| 基礎トークン | 値 | 役割 |
|---|---|---|
| `palette.main` | `#0B0B0D` | 本文、見出し、選択状態、重要な境界 |
| `palette.sub` | `#FFFFFF` | 画面、入力面、青・黒に重ねる文字 |
| `palette.accent` | `#0171E3` | 主要ボタン、キーボードフォーカス |

この3色だけをHEX定義する。補助面・線・薄い文字は `colorRecipes` で墨黒と白を混ぜて生成する。これらは追加のブランド色ではなく同じ基礎色の階調。hover・pressedは青と墨黒を混ぜて生成し、影と背景マスクは墨黒の透明度を使う。混合比と用途の正本は `src/design/tokens.ts`。

| 意味トークン（CSS変数） | 生成方法 | 用途 |
|---|---|---|
| `surface` / `input` | 白 | 標準背景・入力背景 |
| `ink` | 墨黒 | 本文・見出し |
| `subtle` | 白に墨黒3.5% | 補助パネル、選択行、軽い状態ラベル |
| `muted` | 墨黒に白36% | 補助本文・ラベル。薄すぎる灰色にしない |
| `line` | 白に墨黒10% | 操作を伴わない区切り |
| `control` | 墨黒に白45% | 入力境界、状態の枠線 |
| `accent` / `on-accent` | 青 / 白 | 主要操作 |
| `accent-hover` / `accent-pressed` | 青に墨黒14% / 26% | 主要操作の反応 |

通常の移動リンク・副操作は墨黒とし、矢印・下線・枠線で操作を示す。青いラベルや青い背景を画面中に散らさない。色の見本画面は例外としてアクセントのスウォッチを表示する。

### 状態の表現

- 期限超過：明示的な「期限超過」と日付、警告アイコン、墨黒の実線枠。
- 本日対応：日付・時刻、時計アイコン、破線枠。
- 完了：完了の文字とチェックアイコン、薄い補助面。
- AIの更新案：未確定と分かるラベルと情報アイコン。差分の「これまで／反映する内容」は見出しと枠で区別。
- 入力エラー：入力に太い墨黒の枠、すぐ下に具体的な修正方法、`aria-invalid` と説明の関連付け。
- 注意・失敗・成功の通知：具体的な文章と必要なアイコン・線種。赤・黄・緑は追加しない。

本文の単色コントラストは4.5:1以上、入力境界・フォーカスと隣接面は3:1以上を検査する。薄い区切り線を入力境界やフォーカスの代用にしない。ダークテーマは未実装で、別途全状態の検証が必要。

## 4. 文字・余白・寸法

本文・フォームは通常16pxを基準にする。小さなメタ情報へ下げた内容が判断に不可欠なら本文へ戻す。表の高密度表示は任意のモードとして検討し、文字を極端に小さくして収めない。

| トークン群 | 初期値 | 適用 |
|---|---|---|
| `type.pageTitle` | PC 32px / 狭幅28px、行高1.4 | 画面名 |
| `type.sectionTitle` | 24px、行高1.5 | 領域見出し |
| `type.body` / `type.input` | 16px、行高1.75 | 本文・入力 |
| `type.label` | 14px、行高1.5 | ラベル |
| `type.meta` | 12〜14px、行高1.5 | 補助情報。用途別に値を確定 |
| `space` | 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 120px | 中央スケール |
| `layout.relatedGap` | 8〜16pxから意味別に割当 | 関係が近い情報 |
| `layout.groupGap` | 24〜32pxから意味別に割当 | 同じ領域のまとまり |
| `layout.sectionGap` | 32〜48pxから画面種別に割当 | 業務画面の章間 |
| `layout.readingMax` | 720px | 長文の読み幅 |
| `layout.pageGutter` | PC48px / 狭幅24px | 外側の余白 |
| `size.row` | 56px、複数行は内容に合わせ拡張 | 一覧行 |
| `size.action` | 高さ48px | 主ボタン・標準入力 |
| `size.touchTarget` | 44px以上 | アイコン等の操作領域 |
| `radius.media` / `card` / `panel` / `pill` | 8 / 12 / 16 / 999px | 役割別の丸み |

範囲を示した行は、実装時に用途別トークンへ分け、コンポーネントが任意値を選ばない。行高や固定高で長い翻訳を切らず、必要なら高さを広げる。日時・金額の数値は桁を比較しやすくし、比較表では小数桁・通貨・単位を揃える。

日本語の見出しの字間は標準とし、ロゴ用の詰めを適用しない。日本語は可読性のあるサンセリフ、欧文と各言語は適切なフォールバックを中央設定する。原サイトの商用書体を同梱しない。フォントの具体的な配布物・採用ライブラリは実装時に選定する。コンデンス書体は必要な短いブランド表現に限定し、顧客名・日本語本文・長い翻訳には適用しない。装飾のための英字ラベルを足さない。

## 5. スタイルとテキストの正本

以下は本番の予定構成。現在のサンプルでは `src/design/tokens.ts` を実装済みで、CSSは `prototype/assets/styles.css` に生成する。UI文言は `src/i18n/messages.ts` に日英を中央管理し、本番時に言語別ファイルへ分割する。共通React部品は未実装。

```text
src/design/tokens.ts           # 型付きの基礎値・意味トークン・テーマ
src/design/generated.css       # トークンから生成するCSS変数。直接編集禁止
src/design/component-variants.ts # ボタン・面・密度などの共通variant
src/components/ui/             # 採用ライブラリをRelayの見た目へ統合
src/components/workflow/       # 案件・タスク・根拠などの業務部品
src/i18n/locales/<locale>/      # 共通・案件・レビュー・取込等の翻訳リソース
src/i18n/config.ts             # 言語、フォールバック、表示形式
```

基礎値 → 意味トークン → 部品variant → 画面の順で使う。現在は `palette` → `colorRecipes` / `colorTokens`、文字と余白は `primitives` → `componentTokens` → CSSの順に接続する。画面や部品が本文サイズ・セクション見出しを独自に上書きしない。「デザインと構成」の色・文字・余白見本は同じトークンを参照する。モダンなUIライブラリのCSS変数やテーマも同じトークンへマッピングし、第二の色・余白体系を作らない。トークンの外部交換形式が必要になったらDTCGへの変換を検討するが、参照キットの生成器があるとは仮定しない。

### 禁止・許容の境界

- 禁止：画面側のHEX/RGB、独自のpx/rem値、任意値のutility、独自のshadowやduration、数値z-indexの直書き。
- 許容：意味付きのクラス・variant、中央トークンに対応するutility、Grid/Flexなどの構造ルール、内容に応じた自然な伸縮。
- 画面固有の値も必要なら中央の画面別トークンへ追加し、理由を記録する。生成CSSは編集しない。
- グラフの座標・進捗率・仮想スクロール位置などのデータ由来の動的計算は、見た目のハードコードとは区別する。単位と範囲を型付きで扱い、見た目の定数はトークンを参照する。
- 翻訳対象：見出し、ボタン、ラベル、placeholder、aria-label、エラー、空状態、通知、日付表示、引き継ぎ文の固定部分。
- 顧客名・元の発言等の業務データは翻訳キーへ変換しない。翻訳表示が必要な場合は原文と区別して保持する。
- 文を文字列連結で組み立てず、翻訳側の変数と複数形を使う。日付・金額はlocale対応formatter、余白・位置は論理方向で表す。

## 6. 共通部品の契約

参照資料の部品をRelayの仕事に合わせて整理する。名称の採用は原サイトと同じ実装であることを意味しない。

| Relay部品 | 役割・構成 | 必須の挙動 |
|---|---|---|
| AppShell / CompactHeader | 現在地、ナビ、ユーザー | 狭幅メニュー、現在地、固定要素による遮蔽防止 |
| PageHeading | 画面名、件数、短い説明、主要操作 | 長いタイトル、多言語で折り返し |
| PrimaryAction / SecondaryAction | 動詞と対象、優先順位 | hover / pressed / focus / disabled / loading |
| FilterChip / FilterBar | 条件、選択状態、件数 | 単一・複数選択の意味、解除、結果件数通知 |
| CaseList / DataTable | 名称、状態、担当、期限 | 表の見出し・ソート状態・キーボード操作 |
| CaseSummary | 現在状況、次の対応、未確認 | AI提案と確定情報を区別 |
| EvidencePanel / Timeline | 元の発言、出典、日時、変更履歴 | 削除・不明・未取得も表示。重要根拠への移動 |
| ProposalDiff | 変更前後、理由、根拠、操作 | 競合、却下、修正、処理中、二重実行防止 |
| FieldGroup / Choice | label、入力、補足、エラー | 値の保持、エラーの関連付け、必須と任意 |
| Disclosure | 補足の開閉 | 読み上げ可能な開閉状態。重要条件は閉じない |
| Dialog / Sheet | 集中する作業、終了操作 | Esc、フォーカス管理・復帰、背面操作抑止 |
| StatePanel / Feedback | 空・失敗・保存・権限・古い情報 | 理由と次の操作。toastだけに重要情報を置かない |
| ComparisonMatrix | シミュレーション条件と数値 | table構造、単位、丸め、前提・更新日、領域内スクロール |

リンクは移動、ボタンは状態変更として使い分ける。タブは矢印キーを含むタブの契約を満たし、一覧フィルターとは分ける。カード全体のリンク内へ別ボタンを入れるなど、操作の入れ子を避ける。

## 7. Relayの画面レシピ

| 画面 | 優先する順序 | 避けるもの |
|---|---|---|
| 今日の対応 | 基準日時 → 今日必要な仕事 → 理由 → 担当・期限 → 次の操作 | 意味の薄い大きなKPI、全カードへの色塗り |
| 案件一覧 | 名前・件数 → 検索・条件 → 案件行 → 詳細 | 冒頭の巨大な画像、長文の一律省略 |
| 案件詳細 | 顧客・状態 → 次の対応 → 並行タスク → 根拠と経緯 → 記録 | 全項目の均等な強調 |
| 更新案の確認 | 対象 → 変更前後 → 根拠 → 未確定項目 → 反映操作 | 未確認の担当・期限を確定風に見せる表示 |
| 情報の取込 | 方法 → 対象・期間 → 処理状況 → 失敗内訳 → 更新案 | 処理中に成功件数を確定表示すること |
| シミュレーション（将来） | 条件 → 結果比較 → 内訳・前提 → 保存・共有 | 根拠のない削減額、単位のないグラフ |

PCの詳細は情報量に応じてサイドパネルまたは専用ページ、狭幅は読み順を保った一列を基本とする。初期プロトタイプの全案件モーダルを固定仕様にしない。

## 8. レスポンシブ・動き・素材

390 / 768 / 1440pxを代表検証幅とする。ブレークポイントは中央定義し、画面全体と部品の配置領域を分けて設計する。カード列数は余地に合わせて減らし、一律縮小しない。

全6画面と共通ダイアログの初期実装は、480px以下、768px以下、1024px以下、それ以上で段階的に配置を切り替える。幅は `src/design/tokens.ts` で一元管理する。

- 案件一覧：PCは表、タブレットは2列カード、スマートフォンは1列カード。同じ検索・担当・状態条件を表とカードへ反映し、非表示の表示形式は操作・読み上げ対象から除く。
- 狭幅：フィルター、記録フォーム、変更前後、カラー見本は縦に並べる。480px以下では数値の集計も縦並びにしてラベルを縮小しない。
- 長い案件名、翻訳文、根拠、保存したメモは折り返す。Grid/Flexの子要素が内容の最小幅で画面を押し広げないようにする。
- ダイアログは表示可能な高さに収め、内部をスクロール可能にし、閉じる操作を上部に残す。Visual Viewportの実測値を中央CSS変数へ渡し、キーボード表示時の可視領域に追従させる。これはデータ由来の動的寸法であり、画面固有の寸法の直書きではない。
- 横向きなど高さの少ない画面ではナビゲーションの固定を外す。開いたメニューは可視領域内でスクロールさせる。安全領域の余白を確保する。

表は見出しと列の意味を維持する。必要な横スクロールは表領域に閉じ、本文全体を横スクロールさせない。フォームは縦積み、主要操作は指で押しやすくする。200%拡大と320px相当の狭い読み幅でも主要な情報と操作へ到達できることを確認する。

動きは操作反応160ms、パネル280ms、紹介ページの初回出現600msをトークン初期値とする。検索結果・入力エラー・数値表示を演出のために待たせない。`prefers-reduced-motion` では移動演出・自動スクロールを止め、状態変化は伝える。

写真は業務上の対象理解に役立つ場合だけ使う。資料は読めるプレビュー、装飾画像は主題が失われない構図とし、読み込み前に領域を確保する。画像のない状態でも名称・状態・操作を残す。動画が必要なら停止手段と静止画代替を用意する。

影は浮いたパネルの意味がある場合に限定し、通常の一覧カードは面と線と余白で区別する。

## 9. 状態の設計

| 状態 | 必須表示・操作 |
|---|---|
| 初回の0件 | 理由と、最初の一歩 |
| 検索結果0件 | 適用条件と解除 |
| 読み込み | 領域を維持し進行を通知。仮数値を確定値に見せない |
| 入力エラー | 項目近くの理由・直し方、値の保持 |
| 部分失敗 | 成功・失敗を分け、失敗部分だけ再試行 |
| 保存中 | 二重操作を防ぎ、保存済みと区別 |
| 保存完了 | 保存した対象を伝え、不要な画面遷移をしない |
| 権限不足 | 理由と可能な操作。機密情報は権限に従って非表示 |
| 古い情報 | 最終取得時刻と対象範囲。案件自体の遅延と区別 |
| 競合 | 変更前後を比較し、意図しない上書きを防ぐ |
| 取消・削除 | 対象と影響を表示。必要に応じて確認・取り消し手段 |
| AIの不確実性 | 不明項目、候補、根拠、解消方法。確信度だけに依存しない |

## 10. 合格基準と進め方

- 見出しだけで対象・現状・次の行動が分かる。
- 通常文字のコントラスト4.5:1以上、大きな文字3:1以上を製品の合格基準とする。入力境界・フォーカス等も背景との識別性を検証する。
- 操作領域は44×44px以上をRelayの目標とする。文字サイズや行間を下げて合わせない。
- キーボードのみで操作でき、フォーカスが見え、固定領域に隠れず、モーダル終了後に戻る。
- 日本語・英語の長文、擬似翻訳、RTL、数字の桁増加、欠損、0件、失敗、無効状態を確認する。
- 読み上げ順と視覚順が一致し、状態が色だけに依存しない。
- 値と表示文言が中央管理され、同じ役割に同じトークン・部品を使う。
- 必要な状態遷移とAPI結果を表示へつなぎ、成功を先に断定しない。
- 実測していない性能・アクセシビリティ・原サイトとの一致を「検証済み」と報告しない。

実装は一覧・詳細・更新案またはフォームの代表3画面から始める。通常・失敗・狭幅の見え方を確認してから共通部品として広げる。トークン変更時には3画面すべてへの影響を確認する。

画面サンプルは本ガイドに沿って刷新した。本番UI・認証・DBは未実装で、全状態の実ブラウザー検証が完了したことを意味しない。検証範囲は VALIDATION.md を参照。
