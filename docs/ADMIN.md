# Google認証付き管理者ページ

入口は `/admin`。初期版では利用許可アカウント・管理者／メンバーの権限・有効なログインセッション数・Google／DB／LINE／カレンダー暗号化の設定状況を確認する。許可アカウントの追加・権限変更はサーバー環境変数で行う。画面内の追加・編集・削除機能はない。

## 認証と権限

既存のGoogle OpenID Connect（Authorization Code＋PKCE）を共通利用。Googleで確認したメールと、毎回のセッション照会に基づいて認可する。

- `ALLOWED_GOOGLE_EMAILS`：通常の利用許可リスト。
- `ADMIN_GOOGLE_EMAILS`：管理者リスト。**両方に登録されたアカウントだけ**を管理者とする。
- 管理者リストが空・未設定なら管理者は0人。通常ユーザーや最初のログイン者を自動昇格しない。
- メールはカンマ区切り、前後空白を除去し大文字小文字を区別しない。ドメイン全体の許可は行わない。
- リスト中の空項目・不正なメール形式、通常利用リストにない管理者が一件でもある場合、管理者権限を付与しない。一般利用のログイン設定とは分離する。
- 環境変数はサーバー専用。実アドレス・秘密情報を公開コードやクライアント設定へ書かない。

`GET /admin` は未ログインならGoogleログイン画面、一般ユーザーなら403の権限不足画面を返す。許可された管理者だけにアプリシェルを返す。通常アプリのサイドバーには全員に管理者入口を表示する。権限がない場合は鍵と破線、認証が必要な読み上げ名で制限状態を示す。入口自体は操作でき、`#admin` で管理者認証画面へ進む。権限不足・未ログイン時は管理情報を描画せず、Googleログインから `/admin` へ戻る。一般ユーザーの再ログインだけでは管理者に昇格しない。`file://` でもGoogleログインの入口は有効にする。ボタンは公開版の `/admin?lang=...` へ通常のリンクで移動し、公開環境のサーバーで認証を行う。ローカルから管理APIへ通信せず、セッションや下書きをURLへ含めない。公開先は `src/prototype/public-links.ts` に集約し、クエリーや端末保存の値から変更できない。

`GET /api/admin/overview` は未認証401・一般ユーザー403。画面の表示フラグ、URLの `#admin`、ローカル保存、リクエストヘッダーから管理者権限を受け取らない。設定を外したアカウント、期限切れ・削除済みセッションは既存Cookieでも拒否する。API失敗・拒否・再取得中には、以前取得した管理情報を画面から消す。

ページとAPIは既存のprivate/no-store、CDN no-store、正規Origin制約、CSPを継承。アカウント一覧はAPI応答のみで、公開静的ファイルや端末の案件保存へ含めない。レスポンシブの共通部品・日英文言・RTLも継承する。

公開版の管理者入口：[管理者ログイン](https://relay-chi-ecru.vercel.app/admin)。ローカルのプレビューでは遷移先が公開版であることをボタンの補足として表示する。公開版では既存の同一オリジンのGoogle認証開始リンクを利用する。

## Googleログインからの復帰

管理者ログイン入口は `/api/auth/start?destination=admin`。戻り先は `/` と `/admin` の2択。管理者用の固定マーカーをランダムstateへ加え、既存のDBに保存する。コールバックは保存済みstateを一度だけ消費し、OIDCライブラリによるstate／nonce／PKCE／署名等の検証後、保存した戻り先へ移動する。コールバックの任意URL指定は採用しない。

Googleに登録するリダイレクトURIは既存の `APP_ORIGIN + /api/auth/callback` のまま。`/admin` をGoogleのコールバックURIへ登録しない。要求スコープも `openid email` のまま。追加マイグレーションや別のGoogle OAuthクライアントは不要。

管理者用ログインでは、Googleによる本人確認後、セッション発行前に管理者権限を再確認する。一般ユーザーは通常のログインでは利用できるが、管理者用ログインでは拒否し、新しいセッションを発行しない。認証の途中で管理者リストから外された場合も拒否する。管理者設定が空・不整合の場合はOAuthを開始せず、`/admin` の設定待ち画面へ戻す。設定待ちはHTTP 503と更新操作を返し、動作しないログインボタンは表示しない。

## 設定と利用開始

1. [Google認証・DB設定](AUTH_LINE.md)を完了する。
2. 対象Vercelプロジェクトのサーバー環境変数に、利用許可リストと管理者リストを設定する。`.env.example`に空の設定名のみを記載。
3. 安全に読み込んだ対象環境の変数に対して `npm run check:auth-config` を実行する。不足・形式不正・許可リスト間の不整合があると終了コード1を返す。
4. 対応コードをマージ・デプロイし、設定反映後に `/admin` へアクセスする。
5. 実Googleアカウントで管理者の往復、一般ユーザーの403、権限削除後の拒否を確認する。

ローカルの確認には、Git管理外の `.env.local` を作成したうえで `node --env-file=.env.local scripts/check-auth-config.ts` を使用できる。検査は設定項目名と理由コードだけを出力し、アドレス・秘密値を表示しない。検査だけではGoogle資格情報の有効性、DB接続・マイグレーション、Vercelへの反映を確認したことにはならない。Vercelを自動で書き換えるコマンドではない。

環境変数の変更は新しいデプロイで反映される。PR作成だけでは本番コード・権限設定を変更しない。

設定状況は設定値の有無を表す。DB表示は一覧取得のSQLが成功した場合だけ返す。他の設定表示は実LINE配信や実カレンダー接続を証明しない。ログイン数は期限内のセッション数で、現在オンラインの人数・端末台数ではない。

## 検証

`npm run check` に含まれるサーバーテストは、合成署名付きGoogleプロバイダーとPGliteの実SQLで、管理者への復帰、任意戻り先拒否、未認証・一般ユーザー・偽装フラグ・未設定権限・権限失効・セッション期限・Origin制限・秘密値の非公開を確認する。Reactテストは管理情報の表示、403後のデータ消去、401のログイン導線、503の再試行表示を確認する。

これらは実Googleログイン・Vercel実DB接続・スマホ／iPad実機の表示確認ではない。既存のブラウザーアクセス制限を回避しない。認証に必要な外部設定が揃うまでは本番ログインの利用開始済みと扱わない。

公式資料：[Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)。既存の依存関係を利用し、新たな認証ライブラリは追加しない。

## セッション変更時の画面破棄

表示中の主体（Google subject・管理者権限）はウィンドウ内に保持し、共有localStorageを比較の正本にしない。既存の定期セッション確認で主体・権限の変更、期限切れ、不正な応答を検知したら、Reactルートを破棄して再認証へ移る。モーダルのポータルと管理情報も破棄し、各機能のeffect cleanupで進行中の取得を中止する。遅れて届いた応答やアプリのスクリプトが管理情報を再表示することも防ぐ。

通信失敗時にもルートを破棄し、接続復旧時はページを再読み込みして認可し直す。初回のメニュー権限は検証済みセッションから取得し、古いHTMLの表示フラグを引き継がない。これは確認時に失効を検知する動作で、サーバーからの即時失効通知ではない。表示中の定期確認は既存の60秒間隔を維持する。

`test:session`は実際のセッション起動コードを合成応答で実行し、別ウィンドウが共有ストレージを更新済みの場合、ストレージ拒否、同一ユーザーの権限変更、期限切れ、不正応答、通信復旧を確認する。Reactテストは表示済みデータの破棄、進行中の取得の中止、遅延応答と遅延起動による再表示の防止を確認する。

## 公開ログイン画面の復旧とデプロイ前検査

`/admin?lang=ja` は、管理者向けの説明・Googleでログイン・通常入口へ戻る操作・言語選択を持つサーバー描画のページ。認証操作はJavaScriptが無効でも利用できる。Google認証の開始時に選択言語を設定用Cookieへ保存し、外部遷移後も維持する。正規ホストへ移動するときも正規化済み言語だけを引き継ぎ、任意の戻り先URLは受け付けない。

設定待ち・認証拒否・一時的な接続失敗を別の状態で表す。DB／Google認証開始の障害時にも、生のJSONや接続情報を表示せず、再ログインできるHTMLを503で返す。本人確認後のセッション保存失敗は権限拒否と区別する。APIの認証境界・no-store・Cookie・CSPは維持する。

Google認証の利用開始前に `npm run check:auth-config -- --deployment` を独立して実行する。公開デモのビルドはGoogle設定に依存させない。検査対象は認証変数の形式、管理者と利用者リストの整合性、`APP_ORIGIN` と `public-links.ts` の公開先の一致、ログイン用DBの列・権限。DB検査は読取専用で、顧客行・セッション行の取得、マイグレーション、通知送信は行わない。接続・SQLの待ち時間を制限し、失敗時はGoogle認証を利用開始済みと扱わない。

Google設定とDB接続は独立して検査する。Google設定などに不足があっても、DB URLの形式が正しければDB接続を確認し、両方の問題を同じ実行で報告する。DB URLが未設定・形式不正なら接続しない。DBだけが成功しても他の設定エラーが残る間は検査の終了コード1を維持する。公開デモのデプロイとは別の判定とする。

ログには設定名と理由コードだけを出す。`publicOriginMismatch` は公開先の不一致、`connectionSchemaOrPermissions` はDB接続・認証テーブル・権限のいずれかに問題があることを示す。機密設定を取得し直したり、既存の許可リストを自動で上書きしたりしない。VercelのSensitive変数は管理APIから値を読めないため、取得結果が空でも未設定とは判断しない。

この検査は実際のGoogleクライアントの有効性・同意画面・登録済みコールバックURIまでは証明しない。Google側には `https://relay-chi-ecru.vercel.app/api/auth/callback` の完全一致登録が必要。ドメインを変更するときは公開先・APP_ORIGIN・Google側登録を一緒に更新する。

本番設定を使用した検査用デプロイは `vercel deploy --prod --skip-domain` で作成できる。公開ドメインへの割当は検査成功後に別途行う。PRのマージと公開ドメインの切替は別操作として記録する。


## 再ログイン時の保存失敗

旧セッションの削除と新セッションの保存は、同じDBトランザクションで実行する。新しい保存が失敗した場合は両方を巻き戻し、もともと有効だったログイン状態を保持する。成功した場合だけ旧セッションを無効化し、新しいCookieを発行する。保持された旧セッションも、現在の許可リストと有効期限による照会を引き続き通す。

Googleコールバックの一回限りの消費は、このトランザクションの外で確定する。保存失敗時にも認証コードを再利用できず、Googleでの再認証が必要。テストは実SQLトランザクション内の保存に障害を注入し、旧セッションの維持、途中変更の巻き戻し、認証試行の消費、新Cookieを発行しないこと、正常時の入替を確認する。
