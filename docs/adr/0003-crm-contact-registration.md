# ADR 0003: 顧客に紐付く連絡先を原子的に登録する

2026-09-17 / 実装済み・本番未適用

## 課題

顧客名だけでは実際の連絡相手を記録できない。氏名しか分からない時点でも登録でき、複数の窓口、顧客との関係、主連絡先を区別する必要がある。再送や並行登録で重複・関連の欠落を作らず、既存の所属境界と監査を維持する。

## 決定

- 設計済みの contacts / customer_contacts を 005 の追加移行で実装する。連絡先と関係を同一トランザクションで保存し、関連のない中間状態を API から公開しない。
- 閲覧者は参照、編集者・業務管理者は新規登録。更新・削除権限を追加しない。所属 ID を含む複合外部キーと FORCE RLS で別所属への紐付けを防ぐ。
- 氏名のみを必須にする。メールと電話は任意で、正規化・同一人物の推測・自動統合を行わない。本人確認済みの連絡手段とは表現しない。
- 既存の認可ロックと再送制御を使い、顧客行のロックで追加・アーカイブ・主連絡先登録を直列化する。主連絡先の一意索引を DB にも置く。失敗時は連絡先・関係・監査・再送記録の全体を巻き戻す。
- アーカイブ済み顧客の連絡先は参照できるが、新規追加は拒否する。先に確定した登録の再送では、後続のアーカイブを変更せず登録済み結果を返す。
- 連絡先は 50 件単位で取得し、カーソルを所属・顧客へ結び付ける。本文や監査へ不要な個人情報を複製しない。

## トレードオフと検証

主連絡先の置き換えと連絡先の編集は別の状態遷移になるため、今回は提供しない。顧客行のロックは同一顧客への書き込みを直列化するが、境界の単純さを優先する。検索専用の正規化値は、国・照合要件が決まるまで NULL とする。

PGlite で RLS・入力・再送・監査失敗・HTTP を検証し、実 PostgreSQL で同時再送、主連絡先の競合、アーカイブと追加、所属停止と追加の両順序を検証する。画面は入力保持・操作のロック・保存確定後の一覧失敗・権限喪失・遅延応答破棄を検証する。

本番の移行と既存データによる確認は未実施。今回のテーブル追加では旧コードのテーブル数検査も停止するため、移行・コード反映・切り戻しの手順を検証環境で確認する。
