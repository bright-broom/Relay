# 顧客台帳の実装と利用開始条件

2026-09-17 / 顧客台帳の第 4 段階（連絡先の登録・参照）。ローカル実装と本番適用は別の状態。

## 実装した範囲

- 「顧客台帳」で、所属先を選択し、顧客名・種類を登録、顧客名で検索し、一覧・詳細を再取得する。
- 顧客は所属内で共有する。閲覧者は参照のみ、編集者・業務管理者は登録・編集・アーカイブ・復元できる。
- Google の検証済み subject と固定 issuer から、事前登録した本人・有効な所属へ対応付ける。メールの一致や初回ログインで自動登録・昇格しない。
- 公開デモの架空案件と分離する。顧客はブラウザーのメモリーにだけ保持し、localStorage・sessionStorage・Service Worker へ保存しない。ログアウト・主体変更時は破棄する。
- 登録時は、顧客・監査・再送記録を同じトランザクションで保存する。監査には顧客名や入力本文を複製しない。
- 同じ要求の再送は同じ顧客を返す。同じキーで本文が異なる場合・期限切れの場合は 409。再送時にも現在の権限を検証する。
- 登録、一覧、詳細、再送を追記式の監査へ記録する。監査保存に失敗すると読み取りも成功応答にしない。
- 一覧は 50 件ごとのカーソル方式。時刻のマイクロ秒と ID を保ち、同一時刻でも抜けを作らない。

顧客名・種類の編集と、通常一覧からのアーカイブ・復元を提供する。物理削除、担当変更、status の変更、案件・タスク・料金提案の保存は対象外。連絡先は下記の登録・参照のみを提供する。

更新は version が一致する場合だけ保存する。同時編集・編集とアーカイブの競合では片方だけ成功し、もう片方は 409。画面は入力を保持し、最新の保存内容を併記する。「入力を破棄し、最新の内容に戻す」を選んでから編集し直す。競合を自動的に上書きしない。アーカイブ済み顧客の編集は拒否し、先に復元を求める。閲覧者もアーカイブ一覧・詳細を参照できる。

## 技術判断

既存の React・TypeScript・postgres 接続を維持し、外部サービスや依存パッケージを増やさない。`migrations/003_crm_customers.sql` は設計案のうち 6 テーブルだけを実装する。残りの設計案を自動適用しない。004 は既存データを保持したまま、顧客の更新ポリシー、更新対象列だけの権限、アーカイブ用索引、再送記録の結果版を追加する。005 は contacts と customer_contacts の 2 テーブル、所属境界の複合外部キー、主連絡先の一意索引、RLS と参照・追加権限だけを追加する。004・005 は 003 と同じ所有者で適用する。

認証用の `DATABASE_URL` と CRM 用の `CRM_DATABASE_URL` を分離する。CRM 接続はテーブル所有者・superuser・BYPASSRLS・権限管理者を拒否し、CRM の RLS・所有権・危険なテーブル権限を各トランザクションで検査する。CRM 未設定時は 503 とし、デモ保存へ切り替えない。

RLS の参照依存は本人 → 所属 → ワークスペース → 顧客の一方向。SECURITY DEFINER を使わず、本人の所属照会が再帰しない構造にする。本人・所属・ワークスペースを FOR SHARE でロックし、停止・無効化との順序を直列化する。FORCE RLS の下でも初期登録できるよう、移行を実行した所有者だけに専用ポリシーを設ける。アプリ接続には所有者のメンバーシップを認めない。

FOR SHARE のためだけに、本人の disabled_at・所属の status・ワークスペースの archived_at に列単位の UPDATE 権限を与える。UPDATE ポリシーの WITH CHECK(false) が実更新を拒否する。実行ロールが自分の所属や役割を変更できないことを直接 SQL で検証する。この制約を外してはならない。

DB 接続の資格情報とトランザクション内の本人設定はサーバーの信頼境界に属する。RLS は、侵害されたサーバーが任意の本人設定を行うことまで防ぐものではない。クライアントから主体・役割を受け取らず、パラメーター化した SQL を使う。

参照：[PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)、[CREATE POLICY と行ロック](https://www.postgresql.org/docs/current/sql-createpolicy.html)。

## API

| 経路 | 契約 |
|---|---|
| GET `/api/crm/workspaces` | 本人の有効な所属だけ。100 件を上限とし、超過はエラー |
| GET `/api/crm/customers?workspaceId=...&cursor=...&archived=true` | 同じ所属を 50 件。archived は省略・false で通常一覧、true でアーカイブ一覧。`nextCursor` が null なら末尾 |
| POST `/api/crm/customers/search` | `{workspaceId, query, archived?, cursor?}`。顧客名の部分一致。空文字は全件、上限 200 文字。archived は省略時 false、cursor は省略時 null |
| POST `/api/crm/customers` | `{workspaceId, key, customer: {displayName, kind}}`。キーは UUID、名前は 1〜200 文字、種類は individual / organization / household |
| GET `/api/crm/customers/:id?workspaceId=...` | 同じ所属の顧客のみ。アーカイブ済みも取得可能。対象なし・別所属は 404 |
| GET `/api/crm/customers/:id/contacts?workspaceId=...&cursor=...` | 顧客の連絡先を 50 件ずつ取得。対象なし・別所属は 404。アーカイブ済み顧客も参照可能 |
| POST `/api/crm/contacts` | `{workspaceId, customerId, key, contact: {displayName, email, phone, relationship, isPrimary}}`。連絡先と顧客との関係を一括作成 |
| PATCH `/api/crm/customers/:id` | `{workspaceId, key, version, action}`。action は edit / archive / restore。edit のみ `customer: {displayName, kind}` が必須 |

POST・PATCH は同一 Origin を必須にする。主体と役割はセッション・DB から取得し、入力に余計なフィールドがあれば拒否する。初回登録は 201、同じ要求の再送は 200。全応答に既存の private / no-store を適用する。

検索は保存時と同じ NFKC 正規化・英字小文字化で照合する。`%`・`_`・バックスラッシュは普通の文字として扱い、ワイルドカードや正規表現にはしない。前後の空白を除去し、内側の空白は保持する。メール・電話・読み仮名・表記の推測検索は行わない。名前を変更すると検索用の値も同じトランザクションで更新される。

検索語を URL・ブラウザー履歴へ入れず、POST の JSON 本文で送る。検索の監査は一覧の action に `searched` と `archived` の真偽だけを残し、検索語やそのハッシュは保存しない。インフラ側でも本文をログに保存しない設定が必要。画面内の入力は明示的に検索するまで送らず、所属変更・ログアウト・権限喪失時に消去する。新規登録の成功後は検索を解除して通常一覧に戻す。

新しいページ送りカーソルは所属・アーカイブ条件・正規化した検索語の SHA-256 と結び付ける。異なる条件のカーソルは 400（crmCursorInvalid）として先頭からの再取得を求める。検索語の平文はカーソルへ入れない。ハッシュは匿名化や認可の代わりではなく、各ページで現在の所属権限を再確認する。旧形式のカーソルは検索語が空の一覧に限り互換受理する。検索・一覧は同じ 50 件単位で、同時更新中の全ページを固定するスナップショットではない。

この段階では `strpos` による部分一致と既存の所属・時刻索引を使い、追加サービス・依存・マイグレーションは不要。検索専用索引や大規模データでの性能保証は未実施。既存の DB 実行時間上限を維持し、実データに近い件数で測定してから索引を追加する。

version は正の十進整数の文字列で、JavaScript の Number に変換しない。PATCH の入力上限は 9223372036854775806。成功は 200 で `{customer, replayed, appliedVersion}` を返す。再送は処理時点の最新 customer と、元の操作が適用された appliedVersion を返す。両者の版が異なる場合、画面は後続変更を含むことを明示する。過去のアーカイブを再送しても、その後の復元を取り消さない。

編集・アーカイブ・復元は、本人・所属・ワークスペースの権限行をロックした上で、要求キーの advisory lock → 顧客行の FOR UPDATE → version 条件付き UPDATE → 監査 → 再送記録の順で同一トランザクションへ保存する。監査・再送記録の失敗は顧客の変更も巻き戻す。監査は変更項目名と前後の版だけを保持し、顧客名は複製しない。変更内容が同一でも、受理した編集操作は版を 1 増やして記録する。

登録・更新の通信失敗時は入力・要求キーを画面内で保持して同じ操作を再送する。編集中・結果未確認中は所属・一覧・別顧客の切り替えを止める。登録済みの応答後に一覧の取得だけが失敗した場合は、登録成功と一覧エラーを区別する。画面を閉じると入力・再送キーは破棄されるため、保存結果が不明なまま閉じた場合は、一覧・監査で確認してから再操作する。7 日を過ぎたキーは再送不可。掃除ジョブは未実装で、既存キーを削除して再利用できるようにしない。

## 連絡先の契約

顧客の詳細から連絡先を取得・登録できる。氏名は 1〜200 文字で必須。メールは有効な形式で最大 254 文字、電話は最大 64 文字。メール・電話は空文字で省略でき、DB では NULL とする。前後の空白を除き、電話の国番号・内線やメールの所有者を推測・検証しない。名前・メール・電話の一致で自動統合せず、メール送信・電話発信は行わない。制御文字を含む入力は拒否する。

relationship は contact（担当窓口）/ self（本人）/ billing（経理・請求窓口）/ other（その他）、isPrimary は真偽値。登録時に主連絡先を選択でき、顧客ごとに最大 1 件。既存の主連絡先がある場合は 409（crmPrimaryConflict）とし、先行登録を置き換えない。画面は入力を保持し、通常の連絡先へ変更して再送できる。主連絡先の変更、連絡先の編集・アーカイブ、既存連絡先を別顧客へ関連付ける操作は未実装。DB の関連構造は複数顧客への共有に対応するが、今回の API は毎回新しい連絡先を作成する。

本人・所属・ワークスペースの認可ロック → 再送キーの advisory lock → 顧客の FOR UPDATE の順で取得する。連絡先・関係・監査・再送記録を同じトランザクションへ保存し、一部の失敗は全体を巻き戻す。所属停止と保存、顧客アーカイブと追加、主連絡先の同時登録の順序を固定する。追加が先に成功した場合は、その後のアーカイブで履歴として残る。アーカイブが先に成功した場合、新規追加を 409（crmContactArchived）で拒否する。追加では顧客自体の version を増やさない。

同一キー・本文の再送は現在の権限で再検証し、登録済みの連絡先を返す。登録後に顧客がアーカイブされても、確定した以前の登録の再送は成功できる。新たな連絡先の追加にはならない。本文変更・期限切れは既存の 7 日間の再送契約に従って 409 とする。

メール・電話・氏名は URL、監査本文、端末保存へ複製しない。contact の監査には顧客 ID のみ、一覧の監査には顧客 ID と操作名を記録する。検索用の email_search / phone_search は NULL のままとし、推測による正規化を実装済みとしない。連絡先の参照は所属内で共有される。別の機微情報区分が必要な場合は権限モデルを再設計する。

一覧は連絡先 ID 昇順の 50 件単位。カーソルは所属 ID・顧客 ID・最後の連絡先 ID に結び付け、条件が違えば 400 とする。主連絡先を常に先頭へ移す並び順ではない。同時追加中の一覧は固定スナップショットではなく、先頭からの再取得で最新状態を確認する。編集中は顧客・所属の切り替えを止め、連絡先一覧は入力を保持して再取得・ページ送りできる。

005 の未適用時は、新コードの接続ロール検査が 503 で停止する。移行とコードの反映を検証環境で調整し、旧コードへの切り戻し時もテーブル数の検査で停止することに留意する。テーブル・個人情報・監査を削除して切り戻さない。

## 利用開始手順（本番未実施）

1. 運用責任者が DB サービス・プラン、保持期間、復旧目標、所属内の共有範囲、初期メンバーを確定する。
2. 空の検証 DB で既存のマイグレーションから順番に適用する。003 は `relay_crm_runtime` という NOLOGIN の権限グループを作成するため、マイグレーション主体にはスキーマ作成・ロール作成権限が必要。共有環境に同名のロールがある場合は所有者と用途を確認する。
3. 運用担当者が、CRM 専用の制限された LOGIN ロールを用意し、`relay_crm_runtime` だけを付与する。所有者・BYPASSRLS・superuser・ロール管理・DB 作成・TRUNCATE・監査変更を許可しない。既存認証テーブルへの権限も不要。
4. 検証済み Google issuer / subject を使い、本人・ワークスペース・所属を管理用接続で明示登録する。運用で使う管理ロールの権限設計は要確認。アプリのログインから初期メンバーを自動作成しない。
5. CRM 専用接続を `CRM_DATABASE_URL` に設定する。秘密値を文書・ログ・コマンド履歴へ残さない。認証側の設定・許可リストは既存手順に従う。
6. 本番と同じ接続ロール・接続プールで、別所属・未所属・停止済み・閲覧者の拒否、登録・編集・アーカイブ・復元・競合・再取得・監査・再送を確認する。実機・実 Google ログイン・バックアップ復元を別途確認する。
7. CI・権限・監査・マイグレーションを独立レビューし、必要なリリース承認後に利用開始する。

通常のマイグレーションコマンドは `npm run db:migrate`。この実装作業では本番 DB・外部設定・GitHub の保護設定を変更していない。

## 検証と撤退

- `npm run check`：既存の全検証に加え、設計 SQL、実装 SQL / RLS / API、顧客画面を合成データで検証する。
- `npm run test:crm:postgres`：Docker が必要。固定 digest の PostgreSQL 18.6 を一時コンテナーで起動し、制限された LOGIN、同時再送、同じ版への同時編集、編集とアーカイブの競合、所属停止と更新の両順序を検証する。既存 DB の URL は受け付けない。終了時にコンテナーと一時データを削除する。CI でも必須実行する。
- PGlite や PostgreSQL コンテナーの成功は、実サービスの権限・接続設定や実機表示の合格を意味しない。
- 問題発生時は CRM 接続を無効化して顧客機能を停止する。既存の認証・公開デモ・連携は独立している。コードを戻しても CRM テーブル・監査は削除せず保存し、原因調査・復旧後に再開する。
